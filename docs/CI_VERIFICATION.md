## Enforced checks

The read-only `ci.yml` workflow runs the existing web lint/type/unit/build checks and Go vet/tests, plus:

- `npm run build:web` with a before/after `package.json` version equality check; it does not invoke the orchestration `npm run build` command.
- Full `npm audit` and production-only audit with `--audit-level=low`, so any npm advisory fails pending explicit remediation. No npm advisory exceptions are configured.
- `govulncheck` v1.10.0 via the Go module tool, with Go 1.27.4.
- Gitleaks v8.30.0, installed with `go install github.com/zricethezav/gitleaks/v8@v8.30.0` (the module path declared by that release's `go.mod`). CI checks the working tree and Git patch history reachable from every fetched local ref; `fetch-depth: 0`, explicit remote branch/tag refspecs, and `--log-opts=--all` are used. Output is redacted. `.gitleaks.toml` extends all built-in rules, with three anchored exact-secret exception groups limited by AND to the three approved synthetic fixture files and the `generic-api-key` rule. Neither test paths nor arbitrary hex strings are exempt. The scanner job runs executable fixture-regression tests before its real scans.

The candidate manual beta workflow source retains both owner confirmations, an exact matching version/tag, protected environments, read-only permissions except publication write access, and vulnerability scans of the saved Linux/amd64 web/API images before push. It then invokes the Compose-install harness with those exact local built/scanned candidates before publication. After pushing the same images, it resolves digests, verifies anonymous exact-digest pulls/image-ID equality using an isolated Docker configuration, generates release assets and reruns the harness on the generated digest-pinned Compose. There are exactly two application packages and no setup image. Earlier setup-image scanner/publication steps are historical. Source wiring does not establish an actual successful hosted harness run or publication; preserve scanner pinning, read-only image mounts, no socket and fail-closed findings policy.

The approved release-asset contract is a fixed allowlist: `release.json`, `.env.example`, `docker-compose.yml`, `docker-compose.portainer.yml` and `SHA256SUMS`. Target automation must reject unexpected output/symlinked assets. Both Compose assets must embed literal web/API digests for the exact built/scanned/pushed images, with matching version/source metadata. Source definitions require explicit `DIETLEDGER_VERSION`; no unpublished version is implied. The template contains five empty required secret assignments, not generated values. Runtime `.env`, release.env selectors, installers, setup helpers, keys and arbitrary files are not release assets. The artifact upload uses `include-hidden-files: true` to retain `.env.example`; the release job must verify checksums and name all five assets explicitly. These source contracts still need actual hosted/runtime evidence before publication.
