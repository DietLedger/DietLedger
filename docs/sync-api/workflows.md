# Go API workflows and domain rules

Use [operations](operations.md) for exact methods, statuses and types. These workflows describe only Go HTTP behavior and native client responsibilities. The server is authoritative for saved records, but not every calculation or presentation feature has a Go endpoint.

## Food search, sources and storage

- Search the shared catalog with `GET /api/foods/search?q=...`. Scores and record order are server-driven. Local results use `source: local`; a nonempty first-page local miss may query USDA through the caller's encrypted `fda-api-key` (the legacy key name is not a different food provider). Live results use `source: fda`, and the server attempts to cache them. No live fallback for barcode or FDC-detail lookup. Provider errors can look like an empty local search; `DEMO_KEY` is not used for fallback.
- USDA facts are per **100 g**, not multiplied by `servingSize`. `portions[]` holds food-specific gram weights: a portion representing `amount` units weighs `gramWeight`; for a matching measurement use `requestedAmount / portion.amount × portion.gramWeight`. Unit normalization must not turn unknown units into grams. If no food-specific conversion exists, request an explicit weight or clearly label any accepted approximation. Go's import/rematch uses the canonical factors in `units.go`: g=1, oz=28.3495, lb=453.592, kg=1000, mg=.001; water-like volume estimates ml=1, l=1000, tsp=5, tbsp=15, fl oz=30, cup=240, pt=480, qt=960, gal=3840; `whole` uses a 100 g estimate in supported fallback contexts. These are not universal densities. A zero-calorie food can be valid if another canonical nutrient is positive.
- `fdcId` identifies the exact USDA record; local integer `id`, brand, UPC and nutrient IDs do not. Custom foods are per-100 g nutrient records with local string IDs. Local recipe/custom-food `id` is the normal path ID; `portableId` is immutable cross-instance identity (`dietledger:recipe:<uuid>` or `dietledger:food:<uuid>`), not a replacement path ID or permission. A custom food community list is available; the backend's current share mutation is blocked by a path parsing defect (see catalog), so do not implement it as functioning.
- Food storage defaults are independent of existing ingredient snapshots. Read once for the caller and save against `usda/{fdcId}` or `custom_food/{localFoodId}`. Values are exactly `Pantry`, `Refrigerator`, `Freezer`, `Countertop`. Update an ingredient's own `storageLocation` separately when needed.

## Recipes and nutrient snapshots

Canonical keys and units: `calories` kcal; `totalFat`, `saturatedFat`, `transFat`, `totalCarbs`, `dietaryFiber`, `totalSugars`, `addedSugars`, `protein` grams; `cholesterol`, `sodium`, `calcium`, `iron`, `potassium` mg; `vitaminD` µg. Do not infer missing values from a measured zero. Go bounds ordinary nutrient/amount floats where validated to finite values between 0 and 1,000,000; it does not guarantee that inputs represent medically valid facts.

- `POST /api/recipes` can create the metadata, groups and ordered ingredients atomically. Groups are a JSON **string** encoding `[{"id":"group-id","title":"Vegetables"}]`; each ingredient can carry `groupId`. Example body: `{"name":"Soup","servings":2,"servingName":"bowl","requestKey":"unique-client-draft-id","ingredients":[{"name":"Water","amount":250,"unit":"ml","sourceType":"manual","fdcId":-3,"zeroNutritionOverride":true}]}`. Reuse the same caller/key with the same decoded body after a lost response; a changed payload under the same key returns 409. Ordinary POST without a key is a fresh create.
- `PUT /api/recipes/{id}` merges supplied metadata. Omitted/null ingredient field preserves; `[]` clears; a nonempty array replaces the collection, assigning order from the array and potentially changing ingredient IDs. A single ingredient POST appends. Ingredient PUT is a full snapshot write; do not send a sparse update. Preserve prep instructions (string array), group, link, missing-nutrient metadata and provenance as appropriate.
- For a standard ingredient amount with known grams, each snapshot nutrient is `per100g × grams / 100`. Nutrient fields on ordinary ingredient writes are already **for the ingredient amount**. The Go CRUD routes validate and persist snapshots, not a general-purpose scaling service. A linked recipe amount is a fraction/multiple of the **whole** child recipe (1 = whole recipe); `linkedRecipeId` is a local recipe ID. Source types for ingredients: `manual`, `usda`, `custom_food`, `recipe`. Use a positive FDC ID for USDA; custom food uses the local ID as `sourceKey`. Do not make a fake positive ID or equate the `custom_food` spelling with the food-log enum `customFood`.
- `unresolvedSource` keeps original typed identity (`usda` with `fdcId`, `recipe` with `bundleRecipeId`, `custom_food` with `bundleCustomFoodId`), without a live `sourceKey`, `linkedRecipeId` or positive `fdcId`. `unconfirmedNutrition` holds supplied but unverified facts; allowed bases are `per100g`, `perServing` (positive `servingGramWeight` required), `ingredientAmount`, `unknown`. Explicit `zeroNutritionOverride:true` requires manual, `fdcId:-3`, all-zero nutrients, and no source link; don't infer it from a zero row. Missing-nutrient names are unique canonical keys. Keep unknown/uncertain facts separate from confirmed zero.
- Ordinary recipe totals sum ingredient snapshots; per serving divides by recipe `servings` (1–10,000). `customNutrition` supersedes that sum and is always **whole-recipe** (`basis:"recipeTotal"`). Include all 15 numeric keys, a nonblank `source` (1–2,000 bytes), optional original `sourceLabel` (max 50,000 bytes), and `missingNutrients` as applicable. Go rejects unknown fields in this object. Omit `customNutrition` to preserve it on update; explicitly send `null` to remove it. `description` is independent of preparation instructions. Go canonicalizes linked custom-recipe snapshots from those totals and propagates missing metadata; don't add custom totals to descriptive ingredients. Custom log/plan snapshots for a recipe use `wholeRecipeTotal / recipe.servings × entry.servings`.
- Cooked status is a per-user upsert keyed by recipe, not a list of cooking events. Category joins are separate; global category changes need admin, and recipe attachment/reads are caller-owned.

## Tracking, planning and grocery data

- Person profiles are for nutrition tracking, not authentication or dietary filters. `sex`: `male` or `female`; `activityLevel`: `sedentary`, `light`, `moderate`, `active`, `veryActive` (create defaults when empty). `heightCm` >0–300; `goalWeightKg` >0–1,000. Other goal fields use the units in their names. Explicitly read before full updates. Go stores settings and facts; it does not expose a BMI/BMR/TDEE calculator, daily totals, or clinical recommendations endpoint.
- Log against the profile ID in the URL. Body `profileId` isn't the routing authority. Slots: `morning`, `midMorning`, `noon`, `afternoon`, `evening`, `night`, `snack`. Sources: `recipe`, `customFood`, `manual`; there is no food-log `usda` enum. Non-recipe entries carry consumed-amount nutrient snapshots. For example: `{"date":"2026-02-02","mealSlot":"noon","sourceType":"manual","name":"Lunch","servings":1,"calories":250}`. Sum persisted snapshots for a display total, not snapshots multiplied again by servings. Recipe change does not rewrite historical logs. A custom-recipe log edit that keeps source and portion unchanged retains its historical nutrient snapshot. Changing them uses current authoritative facts. In a PUT response, re-read logs when you need complete metadata.
- Measurements share `/weight` even when no weight is entered. Use kg for `weightKg`, mg/dL for blood sugar and mmHg for pressure. `weightKg:0` is the absence sentinel; render it as missing, not as zero body weight. Other measurements are optional numbers; store `measurementContext` as the supplied string. Server validation protects basic bounds, not diagnostic interpretation.
- Plan by date `weekStart`; list metadata then load entries/groups. `slotTimes` is a JSON value (normally a map from slot to local `HH:mm` strings), not a JSON-encoded string. Updating metadata doesn't move a plan to a different week. Meal/group slots use the log values **except** `snack`. Use server-known recipe IDs for `recipeId` and a group from the same plan for `groupId`; an invalid relationship can surface as 404. Entry PUT merges supplied fields; `null` can clear pointer links. For ordinary entries preserve the saved nutrition when editing unrelated fields; for custom recipes trust the returned server snapshot. Use the actual response IDs and re-read related state after mutation.
- `/api/grocery` persists checklist state; send e.g. `{"weekStart":"2026-02-02","checkedItems":"[\"rice\"]"}`. `checkedItems` is a JSON-encoded array of string item keys. The Go server does not generate the grocery list or merge changes inside the array. If the client offers a derived grocery list, specify stable item-key and conversion rules, handle disagreement across clients, and test them as client-side behavior. Pantry staples are global read-only plus personal; DELETE accepts the **name in JSON** and matches personal names case-insensitively. Re-read after writes rather than assuming a duplicate add's returned ID is persisted.

## Books, templates and sharing

- Read a book and both chapters (trailing slash) and standalone pages. For each chapter, read its recipe joins and chapter pages. Hydrate available recipe details separately. Sort chapters plus standalone pages on shared `position`; chapters interleave recipe joins plus chapter pages on their own shared `position`. When reordering send the complete ordered list: book-level `{"items":[{"type":"chapter","id":"..."},{"type":"book-page","id":"..."}]}`; chapter-level `{"items":[{"type":"recipe","recipeId":"..."},{"type":"page","pageId":"..."}]}`. Refetch after moves/conversions. Detach by recipe ID; move by join ID. Parent/child and destination authorization belongs to Go. Do not call a guessed `/chapters/reorder` route.
- Template type is exactly `recipe`, `book-page`, or `book-recipe`. `layout` is JSON serialized into a string in CRUD, but a raw JSON value in `BundleTemplate`. Store/preserve compatible template metadata without expecting Go to render it; the app can have a separately specified renderer. A global default is readable by sessions and only admin can publish, edit or delete it; another user's private non-default is not admin-readable/editable just because of role. Brand-kit fields are metadata; on PUT, omitted or null `logoDataUrl`/`tagline` preserves, explicit empty string can blank them. Body limits include any data URL bytes.
- Share publication stores caller-supplied snapshot strings (`recipeData`, `tags`), with the server requiring canonical recipe ownership. Decode shared payloads as untrusted content, validate before rendering or importing and never execute embedded markup or commands. `private` is owner-only (others 403), `users` needs valid auth (anonymous 401), `public` is anonymous; stale canonical recipe yields 404. Deleting a share flips it to private. Community searches titles with `q`, exact `category` match and sort `rating`, `most_imported`, or newest default; listings don't deliver snapshots, so fetch by `shareToken`. No Go rating-write endpoint despite rating counters in the wire type.

## Dietary criteria and settings

- `allergens`, `dietaryTags` and `nutrientThresholds` are JSON **strings**, not arrays directly. Allergens: `milk`, `eggs`, `fish`, `shellfish`, `treeNuts`, `peanuts`, `wheat`, `soybeans`, `sesame`. Tags: `vegetarian`, `vegan`, `glutenFree`, `dairyFree`, `nutFree`, `soyFree`, `eggFree`, `keto`, `paleo`, `lowFodmap`, `dASH`, `mediterranean`, `diabetesAware`.
- A threshold has `nutrient` (canonical key, or `sugar`/`fiber` aliases), optional `dailyMax`, `perMealMax`, `per1000KcalMin`, and `alertLevel` (`warning` or `danger`); numeric thresholds must be finite, nonnegative and ≤1,000,000. `perMealMax` uses one recipe serving; density uses whole-recipe nutrients per 1,000 kcal; `dailyMax` is not evaluated against recipes; `totalCarbs` is not net carbs. `recipe-assessments` reads all caller-owned recipes and returns `match`, `noMatch`, or `notAssessed` with reasons. Missing facts, unresolved sources, invalid yield/calories or absence of applicable criteria are not a pass. Unknown needed facts override a known failure. Neither this route nor allergen-rule CRUD evaluates allergen safety or certifies a diet. Do not present stale results as current or suggest medical treatment.
- The Diabetes-aware starter is provisioned initially; explicit restore returns an existing tagged profile (active preferred) without overwriting edits, or creates the inactive starter (sodium daily max 2,300 mg, fiber min 14 g/1,000 kcal, both warnings). Reads do not reseed deleted profiles.
- Use `PUT /api/settings` with e.g. `{"settings":"{\"exampleClientPreference\":true}"}`. Go merges only top-level keys; preserve unrelated client keys and do not put credentials in settings. Location/seasonal lookup is separate; no client GPS permission is needed to send chosen country and region. Provider secrets should be listed by metadata and read in clear only when explicitly needed; no request/response capture, analytics, crash reporting or cache for plaintext values. The Go API stores secrets and supports USDA search fallback; no generic LLM/provider proxy endpoint is implied.

## Dataset jobs and destructive actions

Admin dataset download keys: `foundation`, `sr_legacy`, `fndds`, `branded`. The status catalog also lists `all`; the download worker does **not** have an `all` mapping. Use the supported four individually. State can move `pending` → `downloading` → `extracting` → `importing` → `completed`/`failed`; not all intermediates are guaranteed. Poll by returned integer job ID with bounded backoff. Multipart upload takes a complete JSON array of `FoodItem` (not a ZIP or raw USDA wrapper), ignores foods with no meaningful nutrients, and may fail after some batches commit. Worker timeout is ten minutes; don't blindly resubmit a disconnected upload. Cache mutation is admin-only shared catalog ingestion; never elevate a bundled recipe's supplied food facts via these routes.

Protect account deletion, personal content reset, global content reset, factory reset, and shared food clearing with explicit confirmation and no automatic replay. The two account endpoints require the caller's own password; the two instance resets also require admin. Incorrect password returns 403. A last-admin account deletion requires `newAdminUserId` for another existing user; the promotion and deletion commit together. When offering a recipe/book backup before deletion, wait until it is actually saved or the user affirmatively declines; a backup failure must not be interpreted as consent to delete. A backup is not a transaction with later deletion and does not include all account data. Invalidate all affected caches after authorized operations. Use disposable isolated test accounts and databases for destructive tests; never run them against a real installation without explicit operator authorization.

Read [recipe transfer details](recipe-transfer.md) for selection, versions, preflight and repair. A 200 import response is not proof that recipes are visible in the main library. Use summary flags, resumption and explicit decisions instead of client-side reference remapping or direct database writes.
