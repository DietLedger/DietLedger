# Native recipe transfer and quarantine

This is the Go JSON protocol; the downloadable **documentation** ZIP is not importable. Use [operation paths](operations.md) and [bundle wire types](wire-types.md). There is no generic device-sync endpoint or any web-GUI dependency.

## Select or back up

1. `GET /api/recipe-bundles/candidates` with Bearer. Filter the returned data locally if needed. Candidate `type` is `recipe`, `book`, `nutritionProfile` or `mealPlan`; `access` is `owned` or, for authorized shares from another publisher, `public` (this label can also represent a `users` visibility share). Candidate IDs are local selection IDs, not permission grants. Selecting one object does not override access checks on dependencies.
2. `POST /api/recipe-bundles/export` with `{ "recipeIds": [...], "bookIds": [...], "profileIds": [...], "mealPlanIds": [...] }`. Use owned books/profiles/plans and recipes owned by or legitimately shared with the caller. Even administrators do not bypass an inaccessible dependency. The endpoint reads main records, not quarantine. Profile and meal-plan selections can bring associated food logs, weights, day entries/groups, and recipe dependencies. To persist a file, save the unwrapped `data` bundle as JSON, not the HTTP response envelope.
3. For all caller-owned recipes/books, `POST /api/recipe-bundles/owner-backup` takes no selection/body. Go reads one consistent snapshot including ingredient order, deliberate zero intent, unresolved/supplied facts, book structure, template/category references and pending imports. No private foreign dependency or non-restorable structure is silently dropped. Validation/assembly failure is an error, not a partial backup. It can return a valid empty bundle. This is not a full profile/log/weight/meal-plan/account export, and it does not cover edits committed after that snapshot. Protect exported data at rest; exports may include private recipes or clinical data.

## Wire envelope and identity

- `format: "dietledger.recipe-bundle"`; readers accept versions 1, 2, 3, 4 as implemented. V1 is legacy; v2 adds portable identity/fidelity fields; v3 adds a versioned `pendingImports` section; v4 carries authoritative custom recipe nutrition, description or nonempty missing-nutrient metadata and can also carry pending state. Write new bundles only with the supported fields of the chosen version; preserve the server's version and metadata when forwarding an exported bundle. Preserve array order and do not discard unknown fields in a pass-through. Unsupported versions are errors, not partial imports.
- Use bundle IDs to connect payloads within the file, not as paths on the recipient. `source*Id` preserves provenance, not recipient identity. Versioned portable IDs preserve authorized cross-instance identity. For legacy entries without them the server assigns/stores portable identities and can reuse authorized origin mappings. Different identities do not merge just because names/nutrients match. Same identity with different content can return 409 without changes; no retain/fork override route exists. Use the local IDs returned/read from the recipient.
- Ingredient `source.type` is `manual`, `usda`, `custom_food`, or `recipe`. The typed reference can remain unresolved when the target is missing, without a live dangling link. `suppliedNutrition` retains unconfirmed information, not a source match. Explicit ingredient positions must be unique, nonnegative and provided for all ingredients in that recipe; otherwise use array order. Order-only changes can be identity conflicts. For explicit no nutrition, preserve deliberate zero intent. See [nutrition fields](workflows.md#recipes-and-nutrient-snapshots).
- `foodItems[]` in an import (even from an administrator) can **never** insert or overwrite the shared food catalog. It is unconfirmed package context, including portions. Only trusted ingestion records can verify matching USDA links. Missing records can cause quarantine on a recipient even when previously trusted on the exporter. Neither a version change nor a source label turns these facts into verified records. Server-authoritative whole-recipe custom totals do not certify descriptive ingredient facts. Global category creation requires a DB-confirmed admin; ordinary users can reuse taxonomy but cannot publish it. Imported templates become caller-owned non-default copies.

## Decision and repair flow

1. POST the raw `RecipeBundle`, or `{ "bundle": <RecipeBundle>, "bookDecisions": [...] }`. Validate syntax/format locally for UX only; authoritative validation and mapping run in Go. A successful response is `Envelope<RecipeBundleImportSummary>`: show created/updated/reused/skipped counts, conflicts, promoted IDs and quarantine/decision state separately. Do not assume every result is a promoted recipe.
2. If `requiresBookDecision`, the first response writes no new library content for that preflight. For each conflicting incoming book show candidate targets; require user selection and explicit `merge` or `replace`. Resubmit the **original** bundle plus `{bundleBookId,targetBookId,targetFingerprint,action}` per conflicting book. Never compute or reuse a stale fingerprint. Merge keeps existing metadata/content and appends incoming chapters/pages. Replace keeps the target book ID and existing recipes but replaces its metadata/organization. Show that consequence before confirmation. A stale target/candidate set yields 409; do not overwrite. If the choice was deferred in a pending batch and is stale, cancel the unaccepted batch and import again for fresh choices.
3. If `requiresDecision` and `pendingImportId` are returned, offer whole-batch `keep` or `cancel` at `/api/recipe-imports/{batchId}/decision` with `{ "action": "keep" }` or `{ "action": "cancel" }`. Keep publishes verified recipes and retains unresolved content for relinking later. Cancel discards only the incoming unaccepted context; older staging and reused live records survive. Accepted imports cannot be cancelled (409); cancellation isn't a library rollback. Book actions can remain deferred until acceptance. A legitimate retry returns existing pending state or the receipt outcome.
4. `GET /api/recipe-imports` resumes owner-only staging. Rows may be decision-only, including records representing another batch's shared staged identity. Resolve the required batch decision first; don't attempt to edit a decision-only row. Use `row.id` as the staged path ID, `batchId` for decisions, and the blocker `ingredientId` for repair (or `new` for adding the first ingredient to an empty staged recipe). Submit `CreateIngredientReq` to the repair endpoint with a valid existing source or a valid deliberate zero choice as applicable. Go verifies the source and scales affected snapshots from trusted records, updates dependent staged parents where needed, and transactionally promotes newly complete recipes. Read `promotedRecipeIds`, refresh the live recipe/book lists, and reload quarantine. Rejected repairs leave staged data intact. After trusted food ingestion, explicit `keep` can reverify an accepted pending batch; exact import retries aren't automatic rematches.
5. Saved owner backups may carry versioned pending context and original placement mappings. Let Go remap the entire envelope on restore; don't strip pending records or replay internal mappings independently. A valid backup can restore content into quarantine where sources are unavailable.

## Retry and consistency

Identical accepted import receipts (including timestamp-only differences) are duplicate-safe. Explicit identical reimport after individual deletion can restore missing recipe/effective book placement claims, with new local IDs. Surviving edits, repairs, deleted/superseded placement semantics and prior decisions are preserved; no automatic Merge/Replace or overwrite is implied. A newly conflicting title during restoration can return 409 without writes and does not offer fresh choices for that receipt. Matching receipts do not prove the records still exist, and payload changes are subject to normal conflict checks. Personal or instance content resets clear their applicable receipts. Never turn ordinary refresh/reconciliation into a replay of the import endpoint.
