# Connection, sessions and HTTP conventions

## Connect to Go, not the GUI

Ask the operator for the HTTPS API origin and approved server revision. Send requests to that origin with the `/api/...` paths in [the catalog](operations.md). Do not use browser automation, a WebView, page routes, frontend source, or PostgreSQL credentials. For key-only connection use the [personal-key protocol](personal-keys.md). There is no OAuth, OIDC, device-code flow or native token exchange.

The Go binary listens on its private service port (`PORT`, default `8080`) and serves HTTP. In the standard deployment it is **not** published as a host port. An operator can route `/api` to it through a trusted HTTPS ingress or supply an existing HTTPS API origin that forwards to Go. The app does not install a proxy, pull container secrets, adopt an existing stack, or deploy anything. Preserve the full `/api` path, `Origin`, `Authorization`, `X-CSRF-Token` and independent `Set-Cookie` headers through the ingress; do not rewrite cookie host/path or enable shared caching. Test that precise transport before claiming it works. The Go auth handler checks `Origin` as a configured string; this is not proof of TLS or a replacement for ingress controls. Never expose the Go listener or database as a public raw HTTP port. Server setup is an operator task: PostgreSQL → Go `bootstrap` (provision roles) → Go `migrate` (apply and grant) → Go `serve` (restricted runtime credentials). Use an approved installation and disposable test data. The app has no access to database, HMAC, or signing secrets.

For **session-based** native auth send `Origin: https://actual-api-host[:port]` (no trailing slash or path), and have the operator include that exact value in `CORS_ORIGIN`; `*` does not satisfy auth admission. Do not borrow another client's origin to bypass configuration. HTTPS and platform certificate/hostname validation are required in production. Explicit `AUTH_ALLOW_INSECURE_LOOPBACK=true` permits only a configured `http://localhost` or literal loopback origin, with a separate development cookie. An emulator host alias or a LAN address is not literal loopback; use approved HTTPS staging for devices. Do not disable TLS checks or platform security policy.

## Session protocol

1. `GET /api/instance/state` before login if the app supports setup or registration. For the first registration only, the operator supplies the unused `setupClaim` via a user-entered secret. Do not embed, save or log it. A successful first account is admin. After a factory reset the prior claim remains consumed: the operator needs a new claim. Later registration respects `registrationEnabled` and does not require the setup claim. Register expects `email`, `password` (at least 8 Unicode characters, subject to the underlying bcrypt 72-byte maximum), and optionally `displayName`; email validation checks `@`, `.`, and max 255 characters. Registration can return 403 (admission/claim) or 409 (unable to register).
2. `POST /api/auth/login` or `/api/auth/register` with the exact `Origin`, JSON content type and request JSON. Auth success is **bare** `{accessToken, csrfToken, expiresIn, user}`; `expiresIn` is 900 seconds. Save the server's `user.id` as the session principal. Bearer tokens are opaque to the client; authorization is checked server-side on every request.
3. Keep the access token in memory. Use a host-only, dedicated native cookie jar scoped to the instance/session. Retain the selected `__Host-dietledger_refresh` cookie (HTTPS, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`). Use platform-protected storage only if persistent sign-in is required, and exclude tokens and sensitive cache from backup. Never extract a cookie from a browser or web view or forward it to another origin. Go also emits multiple clearing cookies for a retired name; do not collapse `Set-Cookie` or use the legacy cookie. For explicit loopback only the name is `dietledger_refresh_loopback`, `Path=/api/auth`, not `Secure`. Duplicate selected cookies fail closed.
4. Use `Authorization: Bearer <accessToken>` for Session/Admin operations. On an auth-specific 401, use a single-flight `POST /api/auth/refresh` with the current refresh cookie, exact `Origin` and `X-CSRF-Token: dietledger` (the `csrfToken` in auth responses). No request JSON or Bearer is needed. Store the new cookie atomically and confirm the returned principal still matches before using the access token. Refresh rotates once per use with a 30-day **absolute** session limit; replay revokes that family, including access. On a lost/ambiguous refresh response, do not replay the old cookie: sign in again. Do not treat other 401s (e.g. invalid login or anonymous users-tier share) as an automatic refresh trigger. A 403 is not token expiry.
5. Serialize login/register/refresh/logout per cookie jar; if multiple workers/processes share one jar, they need real cross-process coordination or isolated jars. Bind queued work and in-flight responses to the originating instance, user and session generation; never retry a former user's mutation with a new user's token. On a definite pre-handler authorization rejection, a single retry after successful same-user refresh is reasonable. For ambiguous transport failures use the replay rules below. Cancel/retire old requests and clear or isolate local state on logout/account/server switch.
6. `POST /api/auth/logout` with the same Origin, CSRF header and current session cookie (no body). It revokes that session family, not all devices. Server success clears the cookie; without a cookie, a 200 does not prove server revocation. If an expired, absent or unrelated cookie cannot be tied to the current session, or the request fails, clear local credentials and report revocation as unconfirmed. Never revoke a different principal's session.

A read-only connectivity check against a disposable/approved instance, with no credentials:

```sh
curl --fail-with-body --silent --show-error "$DIETLEDGER_ORIGIN/api/health"
curl --fail-with-body --silent --show-error "$DIETLEDGER_ORIGIN/api/instance/state"
```

## HTTP conventions

- Use UTF-8 JSON, exact camelCase keys, path encoding for each ID segment and a URL query builder. Decoder behavior varies by route: do not depend on unknown keys, null coercion, fallback routing, or framework redirects. Do not automatically redirect authenticated requests to a different origin. Stored date-only values are `YYYY-MM-DD`; use local calendar types rather than converting through UTC. Timestamps use RFC 3339 with optional fractional seconds; treat separate `time` values as wall-clock times, not instants.
- Most successful objects wrap `{ "ok": true, "data": ... }`; mutations with no payload usually return `200 {"ok":true}` rather than 204. Missing data may be omitted, null, or an empty array as noted. Auth, health/about, paginated lists/search, food stats, and share/community reads are exceptions. Choose decoder per [operation](operations.md), ignore unknown response keys, preserve important JSON-string fields, and do not model all results as one envelope.
- Go handler errors normally use `{ "ok": false, "error": "human-readable text" }`. There is no stable per-field error code; use the HTTP status and endpoint context. Ingress, timeouts and unmatched ServeMux paths can yield non-JSON responses. Typical statuses: 400 invalid body/parameters; 401 missing/invalid session or auth; 403 origin/CSRF/role/visibility/password; 404 missing or out-of-scope resource; 405 unsupported method on guarded routes; 409 conflict; 410 disabled key issuance; 413 body too large; 429 rate-limited; 500 store/server failure; 503 capacity/unavailable. Some legacy paths return 500 or an OK no-op rather than 404 or 400. Don't drive control flow by matching raw server error strings. Present a safe, actionable UI message and redact secrets/health data from diagnostics.
- Ordinary body limit 1 MiB; `/api/recipe-bundles/import` 32 MiB; `/api/foods/seed/upload` 512 MiB including multipart overhead. Ingress can impose lower limits. Go bounds concurrent buffered requests (16) and upload admissions (2), with one active dataset worker. Honor `Retry-After` on 429/503 when present. Back off with jitter for safe reads; distinguish a server's explicit rejection from a connection/read failure with unknown write outcome. Do not blindly retry non-idempotent creates, destructive operations, uploads or refresh. Recipe create `requestKey`, exact bundle import receipts and explicit upserts have their own semantics; no generic idempotency header exists.
- `OPTIONS` is a Go middleware response (`204`, no body); native clients do not need preflight. Go accepts `PATCH` on instance registration but omits it from its CORS allow-methods header; use PUT for portable clients. Do not assume HEAD or other incidental method acceptance is a contract.
- For pagination use server metadata for `PaginatedResponse`. Community search has no total: continue while pages are full, and tolerate duplicates/missing items as rows move. Live USDA fallback may return a different number of rows than `perPage` and is not an upstream paging protocol; do not treat the first result as an immutable snapshot.
- There is no incremental cursor, general change feed, WebSocket sync, tombstone API, ETag/version precondition, or generic conflict resolver. Use narrow reads, reload after writes, invalidate related caches, and distinguish stale/offline from current data. Avoid background write queues until the client has a separately approved reconciliation spec. `updatedAt` is display/cache metadata, not a concurrency token.
