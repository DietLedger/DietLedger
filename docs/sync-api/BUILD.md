# Build stages for a separate mobile repository

Apply these gates to one vertical slice at a time. Passing an earlier stage is not approval to publish, expose an API, or modify a DietLedger installation. The owner decides whether a capability is in scope; documenting an admin path is not a reason to put it in a consumer app.

| Stage | Deliverable | Exit gate / required evidence |
| --- | --- | --- |
| 0. Scope and assumptions | Read the kit, identify the operator and pinned server revision, select Android or iOS and initial user journeys. Write a spec with user value, supported operations, non-goals, ownership/privacy, test strategy, planned docs and open questions. Build an operation-to-feature matrix; label each relevant operation planned, implemented, deferred, unavailable or admin-only. | Human approves scope, platform, security/ingress assumptions and acceptance criteria. Send contract gaps back as questions; do not invent Go endpoints. |
| 1. Repository foundation | Choose the smallest native stack the owner can maintain. For Android use a pinned Gradle wrapper/toolchain and platform-native secure storage plan; for iOS pin supported Xcode/SDK and use Keychain where needed. Set formatting, lint/build/test automation, ignore secret config and use independent debug/release settings. Keep dependencies justified. | A fresh clone builds from documented commands, baseline CI runs on a compatible runner, no real host credentials/signing keys included. |
| 2. Transport and contract | Build one HTTP client with configurable approved HTTPS origin, explicit path encoding, correct DTOs, request limits and endpoint-specific decoders. Use Go types and wire fixtures; ignore unknown response fields and model absent/null/empty distinctly when meaningful. | Failing-first tests become green for bare vs envelope, date-only fields, JSON strings, pagination, 404/409/413/429/503, non-JSON failures and cross-origin redirects. Reach `/api/health` and `/api/instance/state` on a disposable matching deployment. |
| 3. Session and account lifecycle | Add login/logout, controlled registration if approved, per-principal storage, single-flight refresh and account switches. Add an explicit revocation-unconfirmed UX. Privileged/setup actions are off by default unless scoped. | Tests prove correct headers/cookies, expiry rotation, response loss without replay, logout vs refresh, late response/account switch rejection, cache separation and 401 vs 403 handling; verify through the real HTTPS test ingress. |
| 4. First useful vertical slice | Suggested: sign in → food search → read/create recipe or log one entry → reload from server. Keep UI/rendering distinct from HTTP DTOs and business rules; implement loading/empty/stale/error states. | Reproduce acceptance tests before code, verify saved and re-read data, nutrition basis, safe retries, cross-account non-disclosure and cancellation. Perform manual device smoke on the first platform before widening scope. |
| 5. Expand by workflow | Add approved food/storage and recipe authoring, profiles/logs/measurements, planning/checklists, dietary assessment, books/templates/brands, sharing and transfer. Each slice has a spec, TDD, authoritative refetch and a matrix update. Add admin/data deletion only as explicitly requested and with safeguards. | Each implemented operation maps to tests or a justified manual test. Run negative/multi-user checks; validate portion conversions, zero vs missing, custom totals, stale shares, import decisions/conflicts and response loss/reconciliation as applicable. |
| 6. Hardening and release candidate | Review privacy, network timeouts, restart/offline state, cache erasure, accessibility, failure/empty states, localization and performance. Enable appropriate dependency/toolchain checks; create redacted diagnostics and a manual checklist. | CI passes from clean checkout, reviewed build artifact installs on approved target devices, high-risk real journeys pass, and independent devices cannot share auth state. Record toolchain, artifact digest, server build, tests/commands/results and known gaps. No safety/medical claim based on a nutrient screen. |
| 7. Handoff, approval and maintenance | Provide install/build instructions, artifact and platform prereqs, upgrade/rollback and data protection notes, privacy disclosures and support steps. Retain an API compatibility matrix and verify changes against new server revisions before updating the contract. | Owner receives build/deploy or install/manual-test handoff and separately approves any beta publication. Keep signing material and instance secrets private; never imply the server or stack was redeployed because the client built. |

## Minimal acceptance suite

- **Unit:** exact JSON field names/types, omission/null, `checkedItems`/settings/dietary JSON strings, no timestamp conversion of local dates, pagination, nullable fields and request replay classification. If the app derives nutrient summaries, prove gram/portion and per-serving conversions, kcal vs grams/mg/µg, rounding only for display, and missing vs zero. For local derived calculations, use small verified fixtures and document inputs/outputs; never duplicate a Go assessment.
- **Integration:** scripted mock HTTP cases for all implemented DTOs/statuses, cancellation and retry; test real Go/PostgreSQL for critical paths including different accounts, invalid child/parent pairing, expired or rotated session, destructive confirmation, and bulk/transfer cases in scope. Test wrong-role/owner rejection and absence of cross-origin credentials. A mock is not evidence of real API compatibility.
- **Device/E2E:** sign in and restart/re-auth, complete and reopen the chosen food/recipe/log/plan workflow, network loss and refresh recovery, account switch, back navigation and accessible error handling. If transfer is enabled, save JSON, import into another disposable installation, exercise quarantine or conflicting book choices and verify intended round-trip behavior.
- **Manual release evidence:** record which OS/device versions and ingress were tested, exactly what passed/failed, whether tests were mock/real and what remains. Treat app signing, distribution, production deployment and server changes as separate decisions.

A simple client-repo layout is `docs/specs/`, `docs/dietledger-api/`, app sources (`app/` or the platform's default project directory), synthetic test fixtures, and CI. Keep native view state, transport and seed/test data distinct; don't add a module just to follow a diagram. Store redacted drift notes with the snapshot commit and affected operations. Document any coverage intentionally left out rather than claiming parity with all web features.
