# Luxury and light/dark themes

## Objective and user value
The user initially requested Olive Botanical as the default and a selectable Dark Luxury theme inspired by art deco. They subsequently made the dark Luxury appearance the default, requested readable emerald recipe-list/instruction hover, and asked for a separate darker DietLedger icon while light appearances retain the original. They further requested a usable dark variant for every existing theme, plus a matching dark icon if needed. Finally, they renamed Dark Luxury to **Luxury** and requested a matching light variant. These direct requests approve the product changes.

## Acceptance criteria
- Fresh users and users without a saved palette or appearance choice see Luxury in its dark appearance by default. Existing valid palette IDs actually stored in localStorage continue to work and persist across reloads. Historical Vintage Teal selection cannot always be distinguished from no selection: the old hook removed its localStorage key and automatically wrote its default to server settings; do not treat that ambiguous old server value as proof of explicit preference or claim to preserve it. Legacy `light`/`dark` setting values are mode names, not palette IDs.
- Add a clearly named Luxury option to the existing theme chooser, retaining its existing `dark-luxury` identifier for saved-preference compatibility. Its dark variant is art-deco-inspired with rich brown surfaces, emerald and bronze/copper; its light variant uses a coherent light art-deco palette with readable text, controls and focus states.
- Theme selection, saved preference and fallback defaults are coherent across initialization, light/dark mode and settings writes. Avoid modifying nutrition data or existing user content.
- Recipe-list and recipe-instruction hover states in dark Luxury use readable dark emerald, without changing light themes. Dark appearances use a subdued DietLedger icon; light appearances keep the original. Avoid changing print output.
- Existing palette themes expose a practical light/dark appearance control in both Settings entrypoints, apply their existing matching variants, persist the choice, and retain saved palette selections. Legacy onboarding `theme: light/dark` is a display mode rather than a palette; do not overwrite either choice. Luxury honors the user's light/dark selection and defaults dark when no appearance is explicitly saved. Serialize palette/mode writes across hook instances and make the existing backend settings merge atomic, preventing concurrent updates from losing preferences or unrelated settings.
- Ensure selected surfaces and brand-colored badges remain readable in every dark palette (not only Dark Luxury), including nested neutral surfaces. Default first paint on unauthenticated pages receives dark-surface styling. Compliance report paper and its semantic badges use theme-independent readable colors during screen-to-PDF capture.
- No dependencies or unrelated design changes. Preserve all pre-existing uncommitted work.

## Affected systems and testing
Existing frontend theme definitions, initialization/persistence and settings as necessary; focused tests first, then narrow frontend tests, TypeScript and lint. Verify actual appearance and switching in a safe isolated browser when practical; explicitly report if not run. Update PROJECT.md and this spec with results. No deployment or live-data modification implied.

## Open questions
Historical explicitly selected Vintage Teal with no local key is indistinguishable from no choice, so it receives the new dark Luxury default. Users can select Vintage Teal again. Existing stored palette IDs are preserved.

## Persistence race repair implementation note

The user explicitly requested the independently reviewed persistence repair. Scope is limited to `src/hooks/use-app-theme.ts`, its tests, `PostgresStore.UpsertSettings`, focused Go tests, and this evidence record; retain all other uncommitted work. No deployment, migration, dependency, or API-contract change.

- Preserve shallow partial-object merge semantics, empty/null no-op updates, validation, row identity and unrelated user settings. Merge in a single PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` using JSONB concatenation, not a Go read/merge/write. PostgreSQL 17 documents atomic upsert and right-hand-key precedence: https://www.postgresql.org/docs/17/sql-insert.html and https://www.postgresql.org/docs/17/functions-json.html.
- Serialize explicit palette and appearance requests across mounted hook instances in browser selection order. A failed request must not poison later saves or suppress an explicit retry; the final successful request must persist the latest selection. Do not write fallback preferences on mount, rewrite the other preference key, or enqueue duplicate pending selections. Failures are not automatically retried; the existing local selection remains visible and another explicit selection can retry.
- First reproduce lost disjoint settings with controlled concurrent PostgreSQL writers for both missing and existing rows; then implement and run focused Go tests with a fresh loopback-only disposable PostgreSQL 17 container. First reproduce frontend overlap with deferred API requests; then cover ordering, both selectors, failure/retry, duplicates, and unmount/remount without resetting the queue.
- Verify with `npm test -- src/hooks/use-app-theme.test.tsx src/components/app-nav.test.tsx 'src/app/(app)/layout.test.tsx'`, `npx tsc --noEmit --pretty false`, focused ESLint, `git diff --check`, and `TEST_DATABASE_URL=<disposable-only> go test -count=1 -race -run 'Test(UpsertSettings|Settings)' ./...` from `sync-server`. Stop/remove only the owned database fixture. No visual/layout change is intended; deferred-request hook tests verify network ordering, not a full browser journey.
