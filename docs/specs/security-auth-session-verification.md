# M7/M9/M10 authentication contract and verification

Approved implementation scope: security release plan, isolated auth worktree only. No deployment, publication, application database, provider, credential rotation or history rewrite operations.

## Contract

- `POST /api/auth/register`: `{email,password,displayName,setupClaim?}`. First user requires the installation's configured minimum-32-character `SETUP_CLAIM_SECRET`; its SHA-256 consumption receipt persists outside factory-reset inventory. Stable `instance_meta` row lock serializes admission policy, claim use, creation/default-profile provisioning and membership writes. After a factory reset, the operator must set a NEW claim and update/recreate the API through its original deployment manager; restarting an existing container does not change its environment. See [claim recovery](../docker-registry-install.md#reruns-upgrades-and-recovery). Old consumed values never reopen setup. Existing installations retain accounts/data.
- Register (201), login (200), refresh (200): `{accessToken,expiresIn:900,user,csrfToken}`; never a JSON refresh secret. Access JWT includes `sid`, `sub`, `type=access`, required expiry; exact HS256 or RS256 configured algorithm only. PostgreSQL active-session lookup on every use makes revocation effective immediately (already-running requests are not cancelled).
- One session/family per login. Random 32-byte refresh material is stored only as SHA-256 hashes, with immutable 30-day absolute session expiry, one-use transactional rotation, retained used-token receipts and replay revoking the whole session. Current-device logout revokes one session. A tab with an established principal must first confirm the shared cookie still belongs to that principal inside the same Web Lock as logout; a mismatch or unavailable confirmation retires local state, reports server revocation as unconfirmed and must not revoke the other account. The confirmation's access token is not adopted or persisted. The provider passes its displayed principal before local retirement, and delayed confirmation responses cannot continue logout after an account-generation change. Account deletion/factory reset invalidate all affected sessions through cascading user deletion.
- Refresh-cookie integrity contract (approved hardening): HTTPS uses only `__Host-dietledger_refresh`, with Secure, HttpOnly, SameSite=Strict, Path=/ and no Domain attribute. The browser-enforced prefix prevents a sibling subdomain from shadowing a host cookie with an injected parent-Domain cookie; cookie Path itself is not a security boundary. Validated, explicitly enabled loopback HTTP uses a separate `dietledger_refresh_loopback` name with HttpOnly, SameSite=Strict, Path=/api/auth and no Domain. HTTPS never accepts that development name or legacy `dietledger_refresh`; there is no fallback. Multiple cookies with the selected name fail closed instead of first-cookie selection. Successful auth/logout and rejected old-cookie refresh best-effort expire the known host-only legacy paths without reading their values or guessing a Domain; an unknown-domain legacy cookie may remain but is never used. Existing sessions using only the old name must sign in again. Explicit `AUTH_ALLOW_INSECURE_LOOPBACK=true` permits HTTP only for configured localhost/loopback origins. Configure exact public origin(s) in `CORS_ORIGIN`; wildcard/missing origins cannot authorize browser auth. Login/register require an allowed Origin to prevent login CSRF. Refresh/logout require allowed Origin plus `X-CSRF-Token: dietledger` (a fixed non-simple request marker protected by strict Origin/CORS; no cookie-readable CSRF secret or persistent browser credential). A missing Origin is rejected for these browser endpoints. Bearer API resource requests remain supported without Origin.
- Browser access/user credentials live only in memory. Reload bootstraps through a shared refresh flight; all cookie-auth operations are serialized across browser tabs using Web Locks. Without Web Locks, cookie-auth operations fail before network dispatch with an informative error; there is no unsafe per-tab/concurrent fallback. An established tab principal is recorded in memory from `AuthResult.user.id`, not decoded JWT claims. Refresh must return that same principal before its access token can be adopted or any request retried. A mismatch increments the local generation, removes local credentials and emits the unauthorized event without logging out/revoking the other tab's valid server session. Fresh reload with no established principal may adopt the current cookie user. This is a cache/request identity guard; Go remains authorization authority, and BroadcastChannel is only a best-effort UI notification. No credential localStorage persistence. Cleanup removes the three known legacy auth storage keys; unrelated origin storage is untouched. The shared legacy-worker cleanup is awaited on logout/account switch. If retirement returns `reloadRequired`, logout warns visibly and login/register refuse to proceed until all DietLedger tabs are reloaded/closed. Logout clears query and in-memory state and calls the server; failure must not be represented as successful server revocation.
- Legacy stateless JWTs lack a live sid and fail. Plaintext users.api_key is cleared/nullable and never issued/read by auth. Managed API-key list/revoke remains, POST issuance returns 410 until a separately specified scoped authentication implementation exists; UI states keys cannot authenticate.
- Sensitive API success and error responses use Cache-Control: no-store. Missing account/wrong password share one error and dummy bcrypt path; duplicate registration yields HTTP 409 with the generic `unable to register account` error and no SQL detail. The owner delegated the policy choice; preserving immediate-registration UX with this documented existence signal was selected instead of adding a verified-account flow. HTTP 201 versus 409 is intentionally not described as complete enumeration resistance; sensitive-membership installations should disable public registration.
- Last administrator cannot be removed/demoted without a successor in the same stable-lock transaction. Factory reset is the deliberate password-gated exception, preserving claim receipts.

## Slices and checks

1. First-claim/session HTTP regression, migration 000036 and store/auth transport; focused PostgreSQL tests.
2. Membership/replay/concurrency/failure tests, minimal guarded transactions; focused then full serialized Go suite.
3. Memory API client/bootstrap, setup claim and dependent consumers; Vitest RED/GREEN, type/lint checks.
4. Privacy/docs and review. Legacy worker retirement is coordinated outside this slice; it needs separate real-browser evidence.

## Cookie integrity hardening acceptance

Before implementation, add focused regressions showing that an attacker-owned valid session under the old unprefixed name cannot establish a fresh HTTPS browser principal; that duplicate selected names are rejected; that a genuine prefixed HTTPS refresh rotates correctly; and that explicit loopback HTTP uses only its separate development transport. Browser verification must use reserved synthetic hostnames routed directly to loopback, a fresh profile and a local TLS fixture, with no real domain/subdomain operations. Prove the browser rejects a Domain cookie with the production prefix and that an injected longer-path legacy cookie cannot displace the genuine fresh HTTPS session. Attribute-only tests and the established-principal guard do not replace this fresh-principal test.

Four focused cookie-integrity regressions failed before the protocol change and passed afterward against the disposable PostgreSQL fixture. The auth-branch full Go suite also passed (236.8 seconds). These are server transport assertions, not proof of native browser prefix enforcement; the fresh-profile HTTPS fixture and final integrated application rerun remain required. The candidate has not been deployed or published.

Logout-principal follow-up: four focused client/provider regressions failed before the fix and passed afterward (16 focused tests total), with TypeScript and scoped ESLint passing. A stale tab cannot use another account's shared cookie to silently revoke that account; same-principal logout confirms and revokes inside one Web Lock without adopting the confirmation token. Held confirmation bodies retain generation checks. The final rebuilt production-browser HTTP session/worker rerun passed; production HTTPS prefix enforcement remains the separate gate described above.
