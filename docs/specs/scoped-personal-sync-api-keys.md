# Scoped personal keys for independent Sync API clients

**Status: Owner-approved contract; candidate implementation on `feat/12-scoped-personal-sync-keys`. Not released.** Personal-workflow parity includes sharing; account deletion, personal wipes, and key management stay web-session-only.

## Objective and baseline

An existing account owner can provision a separate, revocable key per client via DietLedger web, then connect a phone or other independent client with only an operator-provided HTTPS origin and that key. The client can discover its account and grants, then perform the existing personal Sync API workflows on that account, including ordinary record deletion and publishing or revoking the caller's own shares. It never needs the owner's password, a browser, cookies, a refresh session, or an installation claim. Assumption: the operator already installed DietLedger and the account exists. A key cannot act for another account or use administrator power, even if issued by an administrator. Content deliberately shared with the caller and ordinary shared reference data remain readable under explicit scopes; this does not grant mutations against someone else's data. No anonymous enrollment, instance discovery, new API service, sync feed, mobile code, deployment or publication is in scope.

## Proposed first-release HTTP contract

### Authentication and discovery

Use `Authorization: Bearer <personal-key>`; new keys have reserved `dlpk1_` prefix followed by canonical, unpadded base64url encoding of 32 CSPRNG bytes. The token is opaque to clients. Only one Authorization value is accepted for key requests. Recognize the reserved family before the existing route mux (including public, optional-auth, cookie and preflight dispatch), reject ambiguous/duplicate/comma-joined credentials containing a key rather than choosing one, and never retry another credential or go anonymous. Cookies do not participate on the key path. Legacy keys, query/body credentials and other headers are not authentication methods. Ordinary session/public requests follow the existing pipeline; do not teach `requireAuth`, JWT validation, `optionalAuth` or cookie handlers about scoped key validation.

Use one explicit Go method-and-path table with direct dispatch to the reviewed handlers, not general middleware that hands a key off to the session router. Match the canonical path before mux cleanup/redirect; reject alternate spellings (extra or empty segments, encoded separators/dot segments, unlisted trailing slashes, method overrides, undocumented aliases). `weekStart` is a real calendar date, FDC IDs are positive decimals, and UPCs are digit strings (retain leading zeroes). The authorized key context carries owner ID and grants, not session authority or the account's role. If adapting to existing owner-only handlers, pass a minimal role-free owner context, never the actual admin-capable user. No key debug impersonation or admin scope. Keep global/peer rate and resource limits in effect, with bounded lookup time and no token-derived limiter labels.

`GET /api/auth/key` requires a valid personal key, with no additional scope, no request body or query, and no required `Origin` or CSRF header. It returns `200`, no `Set-Cookie`, and the minimum needed to bind and label the client account. It is not a token exchange or `/api/instance/state` dependency. Example for mocks only (token intentionally invalid):

```http
GET /api/auth/key HTTP/1.1
Host: ledger.example.invalid:8443
Authorization: Bearer dlpk1_MOCK_NOT_A_REAL_KEY
```

```json
{"ok":true,"data":{"contractVersion":1,"account":{"id":"fixture-account-a","displayName":"Sample Account"},"key":{"id":"fixture-key-a","scopes":["profiles:read","diary:read","diary:write"],"expiresAt":"2030-01-01T00:00:00Z"}}}
```

No email, role, access/refresh token, password hash, or key secret in discovery. The client binds requests and local data to the complete HTTPS origin (including port), account ID and current credential generation; retire outstanding work on key/account/origin change. Do not run setup/login/refresh/logout on key rejection. Removing the credential locally is not server revocation. Another installation, even on the same hostname with a different port, is a different origin.

### Boundaries within allowed operations

- **Tracking and planning:** full personal reads and writes, including optional blood sugar, blood pressure and measurement context, normal nutrition snapshots and supported linked-source workflows. Check caller, parent and item together in reads and mutations; verify references and move destinations are owned or explicitly usable under existing visibility rules. Never look up private facts from another owner's IDs. For diary and weight, the path profile and key owner are authoritative; retain existing nutrition/snapshot semantics. Profile delete can cascade to that profile's diary/measurements; present that consequence in the client. It does not authorize the personal wipe endpoint. Foreign-owned cascade targets (for example, a legacy book join or another account's storage default on a published custom food) must not be erased by a key; an affected delete fails closed without disclosing the foreign record. Include all nested, flat-alias and cascade paths in authorization coverage; do not assume a handler's pre-read protects a later SQL mutation.
- **Catalog and preferences:** local reads never touch provider credentials. An explicitly granted `catalog:live` can use the owner's existing USDA credential server-side on a local miss, with redaction and existing bounded upstream behavior; no third-party credential is returned or changed and key traffic never writes the shared cache. Existing session fallback keeps its behavior. Pantry shared defaults, global taxonomy, standard foods and published templates are read-only under keys. Preferences only affect caller-owned non-security state.
- **Sharing:** grant explicit visibility-aware reads and owner-only publication, visibility changes and revocation under existing `private`/`users`/`public` rules. A key can intentionally make its owner's content visible to others; it cannot publish another owner's source or alter another owner's share. Foreign private shares are hidden as missing. Key reads do not increment another owner's view counter. For custom-food sharing, the catalog documents a broken session parser; propose binding the exact key route directly to the existing owner-scoped share operation, without changing the session route or promising new custom-food visibility/unshare semantics. Show the effect of publication when granting `sharing:publish`. Ordinary owner edits/deletion of already-published source records can affect what others see (for example, a published custom-food row is live); disclose that effect for the corresponding write scope. A write scope alone cannot switch a private record to shared.
- **Transfer:** these are explicit cross-domain data grants. Export may include permitted recipe/book dependencies, profile/meal-plan selections, and owner backup with pending import context; import may write caller-owned content/dependencies covered by the bundle. Describe these effects at issuance; related narrow scopes alone never authorize transfer. Match existing visibility/dependency checks and import quarantine. For a key, import/relink must reuse pre-existing global taxonomy or return an authorization error without partial publication; it must never use the owner's DB admin role to create taxonomy or publish a default. Enforce non-default template ownership and publication constraints atomically on key writes, including any races with an admin session publishing a template. An `IsAdmin: false` context alone is not sufficient.
- **Always denied:** account deletion and personal wipe, role/membership/registration/onboarding/instance reset, session and setup operations, API-key and provider-credential management (`/api/keys`, `/api/personal-keys`, `/api/secrets` and children), shared catalog administration, taxonomy writes, default-template administration, unlisted paths/methods and incidental route aliases. Public health/about/state endpoints remain available without a key; they grant no authenticated capabilities. No authenticated `HEAD` or `OPTIONS`. No new bulk delete or security operation is implied by parity.

### Rejection and client behavior

- **401** (`key_invalid`, `WWW-Authenticate: Bearer`): on discovery or a key attempt, missing, malformed/ambiguous, wrong secret, unknown, legacy, expired, revoked or deleted-owner keys are indistinguishable. On existing routes a legacy unmarked Bearer still gets the existing session rejection (no key access). No key material, grant or account hint in 401s. Suspend sends for that credential and prompt for replacement/check origin; do not refresh, replay writes or silently switch accounts.
- **403** (`key_forbidden`): for requests reaching Go, valid key but wrong scope, unlisted method/route, or an attempted administrative action inside an allowed operation, even with owner admin role, correct password in body or valid refresh cookie. Check scope before looking up objects. Don't log the user out or retry with another credential; show feature unavailable for this key. **404** (existing error envelope, same public result for missing and foreign resource) for an admitted operation with an unavailable owner/parent/object; never reveal foreign record existence.
- **400** invalid admitted input; **429** bounded request limit; **503** if key verification storage is unavailable (no handler dispatch, not invalid credentials). Use the existing `{ "ok": false, "error": "…" }` envelope plus stable `code` for the new key-specific 401/403/verification 503 (`key_unavailable`). All key/management responses including errors are `no-store`. Ingress, Next and admission can reject first (e.g. 404/405 for a route/method they do not forward), possibly with non-JSON; these are not grants or reasons to try an alias. Honor `Retry-After` when present. No generic idempotency guarantee: if a create response is lost, reconcile by re-reading; no automatic POST replay. A server that predates the contract may return 404 at discovery; distinguish unsupported server/ingress from bad key and do not guess another protocol.

## Issuance, storage, expiry, rotation and revocation

- **Web only for management UX.** Add a personal key settings surface reachable from both the ordinary user's AppNav Settings dialog and the admin's Settings page; separate from provider secrets and legacy keys, leaving their existing list/revoke contract intact. The new management HTTP routes accept an active session bearer only; never cookies alone or keys. Browser mutations require the exact configured HTTPS web Origin and explicit `X-CSRF-Token: dietledger` marker (no insecure-loopback exception for new key management mutations). POST also requires a fresh check of the current password, rate-limited by peer and authenticated account using fixed buckets; wrong password is 403. Use the session account, not a submitted owner. Do not auto-retry issuance after credential generation changes or an ambiguous result. The phone app never calls management routes.
- **New management routes** (all responses use the existing success/error envelope): `POST /api/personal-keys` accepts `{name, scopes, password}`, requires a trimmed nonempty label (max 80 characters), and a nonempty explicit array of distinct known scopes (no defaults). Returns `201` with `{id,name,scopes,createdAt,expiresAt,key}` in `data`, where `key` is the only plaintext response. `GET /api/personal-keys` returns `200` with the caller's current stored rows (`id,name,scopes,createdAt,expiresAt` only; may include expired until removed; empty array when none). `DELETE /api/personal-keys/{keyId}` hard-deletes the caller's row, returning `200 {"ok":true}` or 404 for missing/foreign. No update, show-secret, or rotate endpoint. `POST /api/keys` **stays 410** for session clients.
- **Separate DB credential.** New `personal_api_keys` table with owner FK `ON DELETE CASCADE`, UUID metadata ID independent of the secret, label, immutable scopes, creation and mandatory expiry, and indexed unique SHA-256 digest of the high-entropy token. No plaintext, encrypted reversible copy, logging, last-used write or reliance on the installation HMAC; do not change operator secrets. Compute digest after bounded syntax validation; look up only in the new table and validate owner, expiry and known scopes against DB on every request (no positive cache). Do not migrate or import legacy keys into this table. Use a controlled migration with existing runtime grants. Proposed fixed **90 days** from issuance and cap **10 stored keys per owner**, including expired rows, enforced atomically (409 when full; remove old rows to free space).
- **One-time delivery.** Return the secret only after commit. Web shows it in transient UI state, clears it on close/unmount/account change, and copies only on explicit action with a clipboard caution. No persistence in URL, browser storage, settings, query cache or service worker. If delivery is lost, list by label/creation time, revoke the orphan and issue a replacement; no recovery by reading a hash. Clients use an OS credential store (e.g. Keychain/Keystore-backed storage or system secret manager) or memory only, exclude keys and private cached data from backup, and avoid analytics/clipboard history. Go, Next, ingress and client must not record Authorization, Cookie, credential-bearing bodies, private response bodies or digests in logs, tracing, diagnostic exports, access-log formats or crash reports. Scope-grant notices should identify clinical data, ordinary deletions/cascades, publication, transfer (including dependency data) and live provider use. Full personal access must be an affirmative choice, not the default.
- **Rotation and immediate revocation.** Issue a new key in web, install and confirm discovery of the same account and intended scopes, then revoke the old key promptly; suspected leak: revoke first. No grace after expiry/delete; requests admitted before revocation may finish, but authorization started after the commit must fail, including from other server processes. Web logout revokes the web session, not issued keys. Match legacy lifecycle: authorized personal wipe removes that owner's keys; admin content reset removes all keys; account deletion/factory reset remove keys with their owners. Serialize issuance with relevant owner/reset locks. Document that restored snapshots can contain previously valid key digests: isolate restores and arrange explicit operator removal of restored personal keys before reopening ingress; no automatic changes to any live database.

## HTTPS ingress

First topology to verify: operator-managed trusted TLS ingress at an exact public `https://host[:port]` origin (e.g. `https://ledger.example.invalid:8443`) → existing private-facing web/Next transport → private Go service → private PostgreSQL. The operator configures the certificate/hostname and firewall/binding, exact browser `CORS_ORIGIN` including any explicit non-default port, and `AUTH_ALLOW_INSECURE_LOOPBACK=false`. Do not change standard Compose ports, add a second public listener/service or open API/DB ports on any interface. The only externally reachable path is HTTPS ingress; any web HTTP upstream is bound/restricted to the trusted ingress path, not reachable by untrusted clients. Protect the internal hop or use authenticated encryption if it crosses an untrusted network. Next needs to forward `/api/personal-keys` and its item route; `/api/auth/` is already forwarded. Direct private-network proxy-to-Go is not part of the initial verified topology.

Preserve canonical paths, explicit methods and Authorization without normalizing disallowed key targets into allowed ones (edge rejects noncanonical raw targets before any rewrite; prove behavior through the built Next path). Reject ambiguous Authorization at the edge if a hop would otherwise collapse or discard it; never forward a key attempt with the credential stripped into a cookie or anonymous handler. Preserve current Origin/CSRF and separate Set-Cookie handling for sessions. Strip client-supplied forwarding/control headers, never infer transport security from `Origin`, `Host`, or an untrusted forwarded header, and disable shared caching and credential capture. The native client validates the operator-entered HTTPS origin before sending a credential, checks certificate trust and hostname, preserves port, and disables automatic redirects for credentialed requests, including same-origin redirects. Do not rely on HTTP redirects for safety or support cleartext/emulator bypasses. No TLS checks may be disabled in testing or production.

## Approved decisions

The owner approved the revised spec as written. The product direction is full personal-workflow parity including sharing; account deletion, personal wipes and key management stay web-session-only. The approved defaults are:

1. **Scopes:** opt-in Full personal access preset with narrower grants available, including clinical fields and ordinary deletions/cascades. The preset does not grow on upgrade.
2. **Integration and sharing:** provider credentials stay web-session-only; explicitly scoped USDA lookup does not write the shared cache. Visibility-authorized share reads and the owner-only custom-food publishing correction are in scope without changing session behavior.
3. **Provisioning:** web management for both roles, session + HTTPS Origin/CSRF + current password at issuance, fixed 90-day expiry, 10 stored keys per owner and issue/replace/revoke rotation with legacy-equivalent wipe/reset invalidation.
4. **Ingress:** operator TLS ingress → private-facing Next → private Go on an explicit HTTPS port, without changing standard Compose service ports.
