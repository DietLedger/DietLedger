# Quarantine empty state and Diabetic filter

## Objective and approval
User requests quarantine page show **“No recipes! good job!”** instead of an error when empty, theme its All books / no-book dropdown, and restore the default dietary filter as a single **Diabetic** button with no warnings or extra copy in the filter section. This explicit request approves the product change. The default is a starting point; people are responsible for their own filter settings, as documentation should state.

## Acceptance criteria
- An empty successful quarantine response displays the exact requested message and no error. Actual network/server failures remain visible and retryable; do not disguise them as empty data. Identify and fix the underlying empty-response issue if necessary.
- The book filter remains usable and legible in light and dark themes, including native options; preserve its existing values and filtering behavior.
- The opt-in dietary filter is available by default as a button labeled **Diabetic**, with no warnings, explanation or extra text inside the filter section. Its existing configurable nutrient-assessment criteria and fail-closed handling are retained; do not invent medical claims or thresholds. Document that defaults are a customizable starting point, not medical certification or a guarantee.
- Preserve existing data, choices and user-owned dietary profiles. After reset or deletion leaves no eligible profile, the button remains visible; clicking it explicitly restores the existing editable starter defaults, not on reads or restart. Owner-scoped serialization prevents duplicate restores and never overwrites an existing edited eligible profile.
- No dependencies, unrelated cleanup, live data operations or deployment. Preserve pre-existing dirty work.

## Scope and verification
Quarantine component/API conversion and focused tests; dietary filter/component/profile provisioning as necessary, focused tests and related product/domain spec documentation. TDD: reproduce errors/missing button before change, then focused green; run broader relevant tests, type check, lint; use a disposable PostgreSQL database when exercising server tests. Browser verification separately where practical. Update PROJECT.md, NUTRITION_DOMAIN.md and `diabetes-aware-dietary-filter.md` if applicable. Record results and limitations below.

## Open questions
Resolved by explicit user approval: keep the Diabetic button visible after reset or profile deletion. Only a user click may restore a missing starter; reads/restarts must not reseed it. Reuse an existing eligible user-owned profile without replacing edits. Concurrent clicks/retries must not create duplicate starters.

## Dietary implementation contract
- `POST /api/dietary-profiles/diabetes-aware-starter` explicitly returns an existing eligible caller-owned profile, or creates the same editable inactive starter used by account provisioning. It accepts no new nutrition criteria. Serialize restore requests per owner; reset and restore use compatible user-first locking.
- One opt-in **Diabetic** button selects the current eligible active profile, otherwise the first eligible profile by the existing list order; no extra profile-name text or selector appears in the filter section. If none exists, click invokes the restore endpoint and selects the returned profile. No automatic restoration on reads, refresh or restart.
- Restore/profile/assessment errors remain outside the filter section. Explicit filter-request intent survives restore failure: pending/failed restoration and missing selected profiles cannot display unverified matches, and Clear remains available. Retry or Clear is required to leave the failure state. Existing assessment rules, threshold values and editability remain unchanged.
- Restore cache writes, invalidations and selection are bound to the originating authenticated user and token plus the mounted caller lifecycle. Logout/account change/token change/unmount must retire pending completions even when `queryClient.clear()` has run; no prior-account response may populate a new session's cache. Keep tokens private in closures, never query keys, mutation variables/context, logs or user-facing errors. Clear invalidates selection intent but does not undo an already accepted server-side restore.
- Regression checks cover absent profile after reset, explicit restoration, saved edits, existing-profile reuse, owner isolation, concurrent/retried restoration, rollback/failure and no read-time reseeding. Parent documentation ownership remains unchanged.
