# Complete custom-data reset

## Authority and objective
The user reported Settings → Delete my data followed by an identical cookbook import yielding “No changes” with an empty recipe list. They explicitly approved **instance-wide deletion of all custom content across all users**, administrator-only, preserving accounts and imported standard nutrition databases. This spec records that approved scope; it does not authorize executing a reset on live data or deployment.

## Implementation contract
- Reuse the existing password-gated, administrator-only `POST /api/instance/reset-user-data`, rather than widening the caller-scoped account endpoint's permissions or silently making a personal endpoint global.
- In administrator Settings, replace the misleading personal-delete shortcut with **Reset all custom data**, explicitly warning that it affects every user. Existing instance reset UI must use the same description. Non-administrator personal deletion may remain caller-scoped for compatibility; it must not clear another user's records or shared global content.
- Preserve accounts/passwords (including the legacy `users.api_key` account credential), login sessions, account settings, instance onboarding/configuration, migrations and imported standard nutrition data (`food_items`, its source metadata/seed job records and any reference tables). Clear all application-generated content: recipes and custom nutrition, ingredients, books/chapters/pages/joins, custom foods, categories, templates, staples, seasonal data, plans/logs/profiles, custom storage locations/defaults/secrets, API keys/devices, completions, recipe-create retry records, import mappings, all import batches/staged payloads and repair receipts.
- Use an explicit audited table inventory and one transaction. No swallowed database errors, no post-success reseeding of staples/custom content. Report failure on any failed deletion/commit; rollback the entire reset. Clear community categories too. Move any startup recreation of those defaults to a one-time migration so fresh installs retain defaults but a reset stays empty after restart. Preserve factory-reset account/onboarding semantics and its default taxonomy/staples initialization: that separate action may explicitly restore defaults, unlike custom-data reset. Avoid unrelated changes.
- Correct caller-scoped deletion's incomplete inventory and swallowed errors where retained; do not turn it into a global operation.
- Clearing import receipts must allow identical native bundles to create fresh recipes/books/placements. Do not change ordinary import idempotence or blindly replay completed batches. Serialize reset with the existing import user-lock boundary before acquiring content-table locks; a previously in-flight import must complete before its rows are cleared. Use the same owner-first ordering for ingredient updates that create a first food-storage default (and explicit default writes), whose user foreign-key lock would otherwise invert the reset lock order. This is not a permanent write freeze: later authorized writes may add content after reset.
- Successful UI reset clears/refetches affected cached data; failures retain current state and surface an error. No new dependencies.

## Affected systems
`sync-server/store_postgres.go`, `sync-server/main.go`, one-time community category migration 000034, reset/startup HTTP and disposable PostgreSQL integration tests; administrator Settings controls and focused Settings/AppNav interaction tests (non-admin popup behavior remains unchanged); PROJECT.md, ARCHITECTURE.md, DECISIONS.md, TESTING_STRATEGY.md, the settings plan and recipe-package API documentation. Retain all pre-existing uncommitted changes.

## Verification / acceptance criteria
1. Focused failing tests precede implementation, run against a unique disposable PostgreSQL database: completed and pending imports plus global/user custom content are cleared for all owners; accounts, settings, sessions and imported nutrition survive unchanged.
2. Public import → reset → identical public import restores complete recipe/book placement with fresh local identities. Retry without reset remains idempotent.
3. Non-admin/wrong-password requests cannot reset; injected database failure returns failure with no partial deletion. Concurrent import and first/default-storage-save regressions protect owner-first lock ordering.
4. Retained personal endpoint clears only caller-owned content/import state and rolls back on failure.
5. UI tests exercise actual admin Settings reset/password/error/success; non-admin cannot access global reset. Focused frontend tests, lint/type check and broader Go checks run as practical. Browser verification is separate and must not be implied by jsdom.
