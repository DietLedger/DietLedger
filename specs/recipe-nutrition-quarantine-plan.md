## Active revised implementation — simple staging and repair

Goal: implement the requested user workflow, not dataset inventory/preflight or a second nutrition workflow. Every imported recipe is staged first; only verified recipes are promoted into normal recipe data. The quarantine page reads staging exclusively and reuses existing ingredient-search/rematch calculations.

Confirmed by the user: **Stop and undo cancels the whole incoming batch**. This workflow covers **new imports only**, with a blank recipe library assumed; do not move existing main recipes or reset any database. Quarantine is persistent and cumulative: unresolved recipes from all accepted imports remain together until repaired, independent of later imports. A new import must never truncate or replace the queue.

Implementation contract before coding: use owner-scoped import batches for native package context plus staged-recipe rows for mutable content. No main writes occur for a batch requiring a missing-link decision until Keep is accepted. Complete input can promote immediately after staging/verification in the same transaction. Accepted batches materialize book structure once and attach each promoted recipe to mapped placement rows, not replay destructive book replacement. Missing source snapshots are not links; packaged trusted food/custom-food records may be imported as dependencies, while absent targets remain unresolved. Reuse the current rematch scaling and total-calculation functions. Ordinary export isolation follows the staging boundary: unpromoted recipe IDs do not exist in main recipes or live book joins and cannot be exported directly; do not add discovery filtering or a second global readiness subsystem. Owner backups need an explicitly versioned pending-import section and a matching restore path, never silent omission of staging.

Review-driven implementation constraints: v3 backup input must verify main-recipe links too, never bypass staging by changing envelope version. Completed batch contexts are receipts, not instructions to replay old food/template content on later imports. An abandoned missing-record choice remains resumable from quarantine after refresh. Source verification preserves unchanged ingredient snapshots (including backup restore); only a deliberately repaired ingredient and affected linked parents recalculate, using the existing stored-total/measurement semantics. Preserve USDA food-specific portions through staged backup/restore so relinking after restore uses the same gram weights. Same-portable-ID authorized food copies must agree or produce a safe conflict, never silently choose a different source. A v3 backup must also be restorable by the public importer: if legacy/manual main content is incomplete alongside staged imports, fail backup generation rather than emit a successful envelope the v3 reader would reject. This does not migrate or reclassify existing main data; the user's import-only/blank-library scope remains unchanged.

## Milestone implementation decisions (before source-fidelity edits)

- Ingredient position is stored as a zero-based integer in PostgreSQL, assigned from ordered create/replace/import arrays; single-ingredient additions append and edits retain position. Read by `(position, id)`; a migration backfills the only provable legacy ordering (current UUID order) without claiming recovery of previously lost drag order. Native bundle ingredient arrays are ordered; older v1/v2 arrays are accepted in their supplied order, with no invented source UUID ordering. Identity reuse compares ordered content, so an order-only changed reimport conflicts rather than silently retaining a different order.
- Add `zeroNutritionOverride` as an additive boolean in existing v2 ingredient records and API writes/reads. Missing v1/v2 fields mean false. Backfill only provable local `manual` / `fdc_id=-3` with zero canonical nutrients and no live source link; neither zero snapshots nor generic manual records imply intent. Enabled intent requires zero canonical nutrients and no conflicting live/source link. Explicit new UI choice must carry the flag; subsequent rematches clear it and non-nutrition edits retain it. Continue to reject changed same-identity content.
- Source-fact persistence uses nullable `unresolvedSource` typed metadata and `unconfirmedNutrition` facts on ingredients rather than repurposing live source keys or canonical calculated snapshots. The package field is `suppliedNutrition`; allowed bases are `per100g`, `perServing` (requiring positive `servingGramWeight`), `ingredientAmount`, and `unknown`, with unit, provenance and canonical nutrients retained. Missing USDA/custom-food/recipe package targets preserve the original typed source reference while local live-link columns stay empty. Unknown source types, conflicting identity fields, mixed/duplicate explicit positions and invalid numeric/basis data remain validation failures. This storage slice does not certify a standard database or make unconfirmed facts resolved nutrition.

## Standard-database research decisions (before inventory/preflight code)

- Repository inventory confirms four supported standard databases: USDA FDC Foundation Foods, SR Legacy, Survey (FNDDS), and Branded Foods. The Full Download is an aggregate artifact, not a fifth database.
- Use `usda:fdc:<fdcId>` as the exact canonical food-record identity for all four. An unchanged FDC record keeps that identity across installations/releases; USDA assigns a new FDC ID when the record changes. NDB numbers, FNDDS food codes, GTIN/UPC values, and upstream history keys remain typed aliases/lineage and never trigger automatic record replacement or content-based merging.
- Dataset/data type, release, source artifact, checksum, importer version, record count, and completion state are separate inventory/provenance. Nutrient IDs remain separate nutrient-definition identities.
- The browser and server currently duplicate the dataset catalog and disagree on current Foundation/Branded artifact releases and the SR Legacy key spelling. Phase 3 must establish one server-owned authoritative catalog before inventory or preflight relies on release metadata.
- Official FDC sources publish all FoodData Central data under public-domain/CC0 terms, including the four supported data types. The low-risk architecture is direct installation from official USDA bulk artifacts plus a DietLedger sidecar manifest. A future mirror should retain the unmodified archive and separate manifest rather than inject DietLedger IDs into USDA rows. No redistribution is authorized by this plan. See `docs/standard-food-identity-and-distribution.md` for citations, dataset-specific findings, residual Branded/trademark risk, and counsel triggers.
